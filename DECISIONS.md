# DECISIONS

Dated decision log. Supersessions are explicit. Per the Scrappy Cut's closing
line, adding anything to its §2 scope requires an entry here and a reason
that is not "it would be easy."

---

## 2026-07-31 — Adopt the Scrappy Cut; keep the existing app shell

**Supersedes:** Build Directive v1.1 §3 and §9; Stack Decision Record §2–§3.

The Scrappy Cut's revised stack (§5) — Next.js App Router, TypeScript,
Tailwind, Supabase Postgres, Vercel, Stripe Checkout on the Foundation's own
account, Supabase Auth for staff and vendors, no member accounts — is what
this repository already was. The Fly.io container decision in the Stack
Decision Record §2 was driven by job load, and the Scrappy Cut's cuts remove
the job load.

**Decision:** rebuild the money core in place rather than starting a new
repository. Auth, checkout, PWA, routing, and the vendor and donor UI stay.
What changed is everything underneath them that touches value.

**Rejected alternative:** a fresh repository. It would have thrown away
working auth and Stripe integration to gain nothing the migration could not
deliver, and would have left two codebases to reconcile.

## 2026-07-31 — `cards.balance_cents` becomes a projection, not the source of truth

The ledger is authoritative. `cards.balance_cents` is maintained by
`post_ledger_transaction()` inside the same database transaction as the
entries, and exists so that page loads do not aggregate the ledger.

**Rejected alternative:** dropping the column and reading `ledger_balances`
everywhere. It touches roughly fifteen files and adds a join to every card
read for no correctness gain, because invariant 3 asserts the two are equal.

**Known gap, accepted.** A column-level `REVOKE UPDATE (balance_cents)` would
prevent drift structurally, but it breaks the `SECURITY DEFINER` projection
path under some Supabase role configurations. The accepted control is
detection rather than prevention: invariant 3 runs in CI and nightly, so
drift surfaces within 24 hours. Revisit if Supabase's role model changes.

## 2026-07-31 — `grants.sql` lives in `migrations/`, not `db/`

Stack Decision Record §4 specifies `db/grants.sql`. That scaffold was written
for the superseded Fly.io stack. Putting the grants in
`supabase/migrations/006_grants.sql` means they run in the migration chain and
cannot be forgotten on a fresh environment, which is the actual point of
rule 2. The directory name is not.

## 2026-07-31 — Card codes become non-enumerable; the format check widens

Scrappy Cut §3a control 1 requires non-enumerable credentials. Existing pilot
codes are `HMLT-0001` — sequential, and therefore a balance-scanning tool
across the whole programme the moment the member view exists.

New codes are `PREFIX-` plus 8 characters of Crockford base32 with the
ambiguous glyphs (I, L, O, U) removed, about 40 bits, generated by
`generate_card_code()`. `validateCardCode()` widened from `[A-Z]{4}-[A-Z0-9]{4}`
to `[A-Z]{2,6}-[A-Z0-9]{4,10}` so legacy pilot cards keep working.

**Consequence:** existing `HMLT-000n` cards remain enumerable. They should be
invalidated and reissued before any card is handed to a member outside the
build team.

## 2026-07-31 — Categories appear on the member balance view

Scrappy Cut §3a lists what the page shows and what it must never show.
Allowed categories appear in neither list.

**Decision:** show them. A member cannot use the card without knowing whether
it buys transit. Categories are a property of the instrument, not of the
person, and the vendor-facing surface already displays them.

This is an interpretation of a gap in the spec, not a departure from it. If
the intent was to exclude them, this entry is the place to overturn.

## 2026-07-31 — Vendor names move off the credential-bound page to `/where`

Scrappy Cut §3a: the member view must never show "vendor names, in any form."
The page previously rendered a "Where to Use Your Card" list filtered by the
card's categories.

**Decision:** the card page links to `/where`, which is not bound to any
credential and shows the same list to everybody. The utility survives; the
disclosure does not. A generic vendor list is a poster on a wall and tells a
person who picks up a card nothing about its holder.

## 2026-07-31 — Transaction history removed from the member view

An earlier commit in this repository added a "Recent Activity" list to
`/wallet/[code]` showing the last ten card events with merchant names and
amounts.

**This was a direct violation of the §3a design rule** and has been reverted.
The rule, quoted so it is not softened by paraphrase:

> "last used at 541 Eatery, Tuesday 6pm" is a location trail on a vulnerable
> person, readable by anyone who takes the card, including a shelter worker,
> an officer, or an abusive partner. Balance is safe. History is a
> disclosure. This is not a v1 deferral; it is a design rule.

Scrappy Cut §8 asks that this line be guarded in code review rather than in a
policy document. Treat any future PR adding history to a credential-bound
page as a blocking review comment.

## 2026-07-31 — Donations fund a pool; cards activate from cleared float

Scrappy Cut §2.4 specifies a pooled lane and a 72-hour clearance hold on
anonymous gifts. Taken literally alongside the QR-scan-a-specific-card donor
flow, these appear to conflict: a donor scanning a card in the street expects
that card to work.

**Resolution:** both hold, in sequence. A gift lands in `donor_clearing` and
clears to `card_float` after 72 hours (immediately for identified donors).
Cards are activated from the cleared float. The card the donor scanned can be
activated straight away against float that has already cleared, so the
recipient gets value immediately and the chargeback risk sits with the pool.

If the float is short, activation still succeeds and drives the float
negative. Refusing would mean an advocate standing in front of a person unable
to hand them a working card because of an accounting timing question. A
negative float is a funding problem, surfaced by the nightly job. It is not a
counter problem.

## 2026-07-31 — Vercel region moved from `iad1` to `yul1`

`vercel.json` pinned functions to Virginia. Every request touching member data
was executing on US soil, against a Canadian-residency commitment.

**Action required, not yet verified:** the Supabase project must also be in
`ca-central-1` (shape decision 6). That is a project setting, not schema, and
cannot be confirmed from the repository. **If the project is in another
region, a new project and a full data migration are required, and doing it
before real money moves is the entire reason this is a shape decision.**

## 2026-07-31 — Stripe Connect removed from the money path

Scrappy Cut §3 replaces Connect with the Foundation's own Stripe account and
a restricted API key. Checkout already used the platform account with no
`application_fee_amount`, so no code changed.

The `stripe_connect_account_id` columns on `charities` and `merchants` remain
in the schema, unused. Dropping them is a migration with no benefit at this
scope, and Connect returns at tenant two.

---

## 2026-07-31 — NFC (`nfc_sun`) resolution is stubbed, not implemented

`credential_kind` exists as an enum from day one (shape decision 4), and
`src/credentials/index.ts` dispatches on it. `resolveSun()` returns a clean
`signature_invalid` failure rather than a silent pass.

Per the tap memo §8, the physical read test across handset families has to
happen before committing to NTAG 424 DNA hardware. The pilot ships
`paper_qr`. When SUN lands, only `resolveSun()` changes — no caller moves,
which is the whole reason the enum was worth having before Sprint 2.

---

## 2026-07-31 — Legacy `redemptions` rows still written alongside the ledger

`/api/redemption/capture` writes both a ledger capture and a row in the old
`redemptions` table, so the admin tables and existing exports stay continuous
across the migration.

**This is duplication and should not survive the pilot.** Once the admin
console reads `weekly_reconciliation` and `settlement_instructions` directly,
delete the `redemptions` write. Tracked as debt here so it is not mistaken
for design.
