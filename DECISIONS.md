# DECISIONS

Dated decision log. Supersessions are explicit. Per the Scrappy Cut's closing
line, adding anything to its §2 scope requires an entry here and a reason
that is not "it would be easy."

---

## 2026-07-31 — Adopt the Scrappy Cut; keep the existing app shell

**Supersedes:** Build Directive v1.1 §3 and §9; Stack Decision Record §2–§3.

The Scrappy Cut's revised stack (§5) — Next.js App Router, TypeScript,
Tailwind, Supabase Postgres, Vercel, Stripe Checkout on the Foundation's own
account, Supabase Auth for staff and vendors, no member accounts — is what
this repository already was. The Fly.io container decision in the Stack
Decision Record §2 was driven by job load, and the Scrappy Cut's cuts remove
the job load.

**Decision:** rebuild the money core in place rather than starting a new
repository. Auth, checkout, PWA, routing, and the vendor and donor UI stay.
What changed is everything underneath them that touches value.

**Rejected alternative:** a fresh repository. It would have thrown away
working auth and Stripe integration to gain nothing the migration could not
deliver, and would have left two codebases to reconcile.

## 2026-07-31 — `cards.balance_cents` becomes a projection, not the source of truth

The ledger is authoritative. `cards.balance_cents` is maintained by
`post_ledger_transaction()` inside the same database transaction as the
entries, and exists so that page loads do not aggregate the ledger.

**Rejected alternative:** dropping the column and reading `ledger_balances`
everywhere. It touches roughly fifteen files and adds a join to every card
read for no correctness gain, because invariant 3 asserts the two are equal.

**Known gap, accepted.** A column-level `REVOKE UPDATE (balance_cents)` would
prevent drift structurally, but it breaks the `SECURITY DEFINER` projection
path under some Supabase role configurations. The accepted control is
detection rather than prevention: invariant 3 runs in CI and nightly, so
drift surfaces within 24 hours. Revisit if Supabase's role model changes.

## 2026-07-31 — Card codes become non-enumerable; the format check widens

Scrappy Cut §3a control 1 requires non-enumerable credentials. Existing pilot
codes are `HMLT-0001` — sequential, and therefore a balance-scanning tool
across the whole programme the moment the member view exists.

New codes are `PREFIX-` plus 8 characters of Crockford base32 with the
ambiguous glyphs (I, L, O, U) removed, about 40 bits, generated by
`generate_card_code()`. `validateCardCode()` widened from `[A-Z]{4}-[A-Z0-9]{4}`
to `[A-Z]{4}-[A-Z0-9]{4,10}` so legacy pilot cards keep working.

The prefix stays exactly 4 — it is a city code, not a variable field. It was
briefly widened to `{2,6}` along with the suffix, which the existing test
suite caught by asserting that `HML-0001` must be rejected.

**Consequence:** existing `HMLT-000n` cards remain enumerable. They should be
invalidated and reissued before any card is handed to a member outside the
build team.

## 2026-07-31 — Categories appear on the member balance view

Scrappy Cut §3a lists what the page shows and what it must never show.
Allowed categories appear in neither list.

**Decision:** show them. A member cannot use the card without knowing whether
it buys transit. Categories are a property of the instrument, not of the
person, and the vendor-facing surface already displays them.

This is an interpretation of a gap in the spec, not a departure from it. If
the intent was to exclude them, this entry is the place to overturn.

## 2026-07-31 — Vendor names move off the credential-bound page to `/where`

Scrappy Cut §3a: the member view must never show "vendor names, in any form."
The page previously rendered a "Where to Use Your Card" list filtered by the
card's categories.

**Decision:** the card page links to `/where`, which is not bound to any
credential and shows the same list to everybody. The utility survives; the
disclosure does not. A generic vendor list is a poster on a wall and tells a
person who picks up a card nothing about its holder.

## 2026-07-31 — Transaction history removed from the member view

An earlier commit in this repository added a "Recent Activity" list to
`/wallet/[code]` showing the last ten card events with merchant names and
amounts.

**This was a direct violation of the §3a design rule** and has been reverted.
The rule, quoted so it is not softened by paraphrase:

> "last used at 541 Eatery, Tuesday 6pm" is a location trail on a vulnerable
> person, readable by anyone who takes the card, including a shelter worker,
> an officer, or an abusive partner. Balance is safe. History is a
> disclosure. This is not a v1 deferral; it is a design rule.

Scrappy Cut §8 asks that this line be guarded in code review rather than in a
policy document. Treat any future PR adding history to a credential-bound
page as a blocking review comment.

## 2026-07-31 — Donations fund a pool; cards activate from cleared float

Scrappy Cut §2.4 specifies a pooled lane and a 72-hour clearance hold on
anonymous gifts. Taken literally alongside the QR-scan-a-specific-card donor
flow, these appear to conflict: a donor scanning a card in the street expects
that card to work.

**Resolution:** both hold, in sequence. A gift lands in `donor_clearing` and
clears to `card_float` after 72 hours (immediately for identified donors).
Cards are activated from the cleared float. The card the donor scanned can be
activated straight away against float that has already cleared, so the
recipient gets value immediately and the chargeback risk sits with the pool.

If the float is short, activation still succeeds and drives the float
negative. Refusing would mean an advocate standing in front of a person unable
to hand them a working card because of an accounting timing question. A
negative float is a funding problem, surfaced by the nightly job. It is not a
counter problem.

## 2026-07-31 — Authorization holds are reaped at the point of use, not by cron

The Vercel deployment failed: Hobby accounts allow at most one cron run per
day, and the clearance job was hourly.

The clearance half of that job does not care — a 72-hour window does not need
hourly granularity. The other half does. Reaping abandoned authorization
holds only once a day would mean a vendor who opens a hold and closes their
phone leaves a member unable to spend their own money for up to 24 hours.

**Decision:** `reapExpiredAuthorizations()` moved to `src/ledger/expiry.ts`
and is now called at the top of `/api/redemption/authorize` as well as by the
cron. Any vendor touching any card releases every stale hold in the system.
The cron drops to daily and becomes the backstop for a quiet day.

**This is a better design than the hourly cron regardless of the billing
constraint.** Self-healing at the point of use bounds the exposure to "until
the next card is used here" — minutes at pilot volume — instead of to a
schedule.

**Rejected alternative:** upgrading to Vercel Pro. It would have bought the
hourly cron and left the 24-hour worst case in place for any period the cron
failed. Paying to keep a weaker design.

## 2026-07-31 — Lost-and-stolen wired end to end

`/wallet/[code]` tells members: "Call us and we will stop this card and give
you a new one with the same money on it." Invalidate stopped the card but
never reclaimed its value, and no reissue route existed. The promise on the
page was not a promise the system could keep — a member who reported a theft
lost their balance as the price of reporting it.

- `/api/cards/[id]/invalidate` now calls `reclaimCard()` **before** flipping
  the state, so a part-way failure leaves a live card with its money rather
  than a dead card holding value nobody can reach.
- `/api/cards/[id]/reissue` is new. It refuses unless the original is already
  invalidated — otherwise it would be a way to duplicate a live card's value
  onto a second card.
- `reissueCard()` derives the amount from the original reclaim rather than
  accepting it as a parameter, so no caller can reissue more than the old
  card actually held.

Six pgTAP assertions cover the round trip, including that the reclaimed pool
is emptied rather than double-spent.

**The ledger boundary lint rule caught a real violation while this was being
written** — the route was reading `ledger_entries` directly to work out the
reclaimed amount. That is what moved the lookup into `reclaimedAmountFor()`
inside the ledger module, which is where it belonged.

## 2026-07-31 — Lookup auditing extended to every unauthenticated card read

Only `/wallet/[code]` was logging lookups. Three other unauthenticated routes
resolve a card by code, and `/api/cards/[id]/lookup` and
`/api/cards/by-code/[code]/lookup` **mint a live signed token** while doing
it. Watching the visible page while leaving the token-minting routes silent
was watching the wrong door.

`src/lib/lookup-audit.ts` is now shared by all four. It logs hit and miss,
and shouts at 12 distinct cards from one source in an hour. Per §3a it logs
and alerts and never blocks: a member checking their balance ten times is
someone budgeting carefully, and it must always work.

Audit failures are swallowed. A logging problem must not take down the page
someone is using to find out whether they can buy dinner.

## 2026-07-31 — Enumerable pilot codes rotated; issued cards go through reissue

`HMLT-0001` … `HMLT-0050`. Guess one and you have guessed all fifty, which
made `/wallet/[code]` a balance-scanning tool across the whole programme.

Migration 008 rotates them to 8 characters of Crockford base32, **except**
cards that have already been issued to a person.

**Rotation is not reissue, and the difference matters.** Rotating changes an
identifier: same `card_id`, same ledger account, same balance, no money
moves. That is right for a card still in a drawer. It is wrong for a card in
someone's pocket — the code printed on their plastic would silently stop
working with no way for them to know why. So the migration checks for an
`issued` event and skips those, naming them in the output.

`scripts/reissue-enumerable-cards.mjs` handles the skipped ones properly:
invalidate (reclaiming the value) then reissue onto a fresh non-enumerable
card, driving the same API routes an advocate would use so the ledger and
audit trail see nothing unusual. Dry run by default.

A `card_code_not_enumerable` CHECK now refuses any new 4-character suffix.
It is `NOT VALID` so already-issued legacy cards are grandfathered until
they are reissued rather than blocking the migration.

`card_code_rotations` keeps the old-to-new mapping permanently — when
someone finds a `HMLT-0007` card in a box next year, that table is how they
learn it was rotated and destroyed rather than lost.

**Every rotated card must be re-printed before distribution.**

## 2026-07-31 — Seed fixed at source; dev users gated; phone fallback removed

Three findings from the Codex audit on `codex/hope-intake-audit`. Two were
real bugs I had missed.

**1. `003_seed.sql` hardcoded enumerable codes.** It looped
`'HMLT-' || lpad(i::text, 4, '0')`, so every *fresh* database seeded fifty
sequential codes. Migration 008 rotates them, which meant a clean apply
seeded the vulnerability and then immediately fixed it — correct end state,
silly path, and a window where it existed.

Fixed at the source: 003 now calls `generate_card_code()`. That function
moved from 005 to 003, the earliest point of need, so there is one copy of
the alphabet rather than two free to drift. 005 keeps a guarded no-op create
for databases migrated before 003 carried it.

**008 is still required, and is not redundant.** It is the only thing that
fixes a database which already ran the old seed — which is exactly what the
live project is. Codex framed these as alternatives; they are sequential.
Fresh applies now report `rotated: 0`.

**2. `003_seed.sql` planted two known-password accounts.** Bcrypt hashes of
`hope-dev-password-1` and `-2`, with advocate privileges — the ability to
load and invalidate cards. Inserted unconditionally, so `supabase db push`
against a project about to take real donations created two accounts whose
passwords are in the git history.

Now gated behind `set hope.seed_dev_users = 'on'`. Default is off; the
migration prints a notice and continues. The profiles and advocate rows are
inside the same gate, since they reference those user ids.

**3. The invalidation phone had a hardcoded fallback, not a placeholder.**
`?? '905-528-7625'` rendered as a live `tel:` link on the lost-card page. I
described this as showing a placeholder in an earlier summary; that was
wrong. It fails badly in both directions — if the number reaches a real
party they start taking calls they never agreed to, and if it reaches nobody
a person whose card was just stolen hears dead air.

The fallback is gone. Unset now renders "Ask your outreach worker, or
anywhere that accepts this card." A missing phone number should look missing.
